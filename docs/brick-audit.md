# Brick Audit & Maturity Tiers (Story 0.9 / D7)

Every brick in `bricks/*/` was audited by reading its `brick.manifest.json`, `migrations/*.sql`, `src/*.ts`, and `test/*.test.ts` files. Tiers are assigned strictly from evidence (D7):

- **`production`** (29 bricks): A behaviour test exercising the named capability end-to-end in `workerd` passes, the brick boots in a preset (or `max-compatible`), and the source has no known capability gaps relative to its summary claim.
- **`beta`** (9 bricks): A behaviour test in `workerd` passes, with known capability gaps (such as default mock provider adapters, local-only gateway URLs, HTTP polling instead of WebSockets, or plain-text/regex subsets) explicitly recorded in `ui.maturityReason`.
- **`experimental`** (2 bricks): Architectural overlap or non-isolated execution (`scripting-sandbox`, `workflow-dag`), with `ui.maturityReason` explaining why and hidden from default `list_bricks` discovery.

The counts above are as of story 0.9. Story 0.11 moved eight bricks to `experimental` as quarantined; see the next section.

## Quarantined Bricks (Story 0.11)

Eight bricks are unsafe or stubs. Each is now `ui.maturity: "experimental"` with a `ui.maturityReason` that starts `QUARANTINED:` and names the problem. Quarantine is reversible: the code, tests and catalog entry stay. A quarantined brick:

- is hidden from `list_bricks` and `search_bricks` unless the caller asks for `maturity: "experimental"`, which lists it (list items stay compact for the token budget; `get_brick` returns its `QUARANTINED:` reason);
- is left out of `max-compatible` (`scripts/max-compatible.ts` records it as excluded with reason `quarantined`), so the attack suite no longer attacks it;
- is in no preset (`presets/*.blueprint.json`) and no Studio starter template.

| **Brick** | **Why it is quarantined** |
| :--- | :--- |
| `admin-console` | The impersonation verify/end routes have no workspace-role check, so any member reaches them (attack suite `ROLE_ESCALATION`), and platform super-admin powers sit inside a tenant app (threat-model risk 4). |
| `oauth-server` | Stub: it issues access tokens that no other brick accepts (only its own introspect route reads them); its authorize route issued codes for any user named in the body until 0.6 (risk 13). |
| `marketplace-splits` | Payouts can double-spend (risk 6), and contracts/balances answer 200 for any vendor id from another workspace (attack suite `ID_GUESS`). |
| `custom-domains` | Stub: `verifyDomain()` reports DNS verified and SSL active without any DNS-over-HTTPS or Cloudflare Custom Hostnames call (fabricated success). |
| `document-pdf` | Stub: writes template text, HTML tags included, as plain lines on a single PDF page with no layout or pagination, and conflicts with `document-parsing`. |
| `realtime-presence` | Room and user lookups answer 200 for a room name or user id from another workspace (attack suite `ID_GUESS`); presence is HTTP polling in D1 with no WebSocket push. |
| `workflow-dag` | Overlaps blueprint workflows (architecture Open question 12) and runs in-process with toy executors rather than durable Cloudflare Workflows. |
| `agent-sandbox` | Stub: only four built-in handlers run; `inline_js`, `http_webhook` and `workflow_call` tools fail `NOT_CONFIGURED`, and there is no isolate sandbox. |

`scripting-sandbox` is `experimental` too but not quarantined: it fails closed when no isolate binding is present, so it stays in `max-compatible` and under the attack suite.

`presets/marketplace.blueprint.json` dropped `marketplace-splits` in story 0.11; its description now says payout splits are experimental. Seller payouts go to the credit wallet.

## Preset Adjustments for Production-Only Bricks (AC 6)

To ensure only `production`-tier bricks remain in the 3 application presets:

- **`presets/ai-credits-saas.blueprint.json`**: Removed `llm-gateway` (`beta`) and `agent-sandbox` (`beta`); added `core-auth` (`production`) and `subscription-plans` (`production`). Resulting 8 `production` bricks: `multi-workspace`, `core-auth`, `credit-wallet`, `subscription-plans`, `metered-usage`, `vector-memory`, `public-api-keys`, `edge-traffic-armor`.
- **`presets/b2b-workspace-app.blueprint.json`**: Unchanged; all 8 bricks (`multi-workspace`, `core-auth`, `rbac-policy`, `audit-trail`, `dynamic-entities`, `outbound-webhooks`, `in-app-notifications`, `feature-flags`) are `production`.
- **`presets/marketplace.blueprint.json`**: Removed `checkout-gateway` (`beta`). Resulting 9 `production` bricks: `multi-workspace`, `core-auth`, `credit-wallet`, `subscription-plans`, `marketplace-splits`, `binary-assets`, `dynamic-entities`, `search-faceted`, `threaded-discussions`. (Story 0.11 later removed `marketplace-splits` as quarantined, leaving 8.)

## Tenant Isolation & Platform Tenancy Architecture (UC6)

### 1. Database-Level Isolation: `scoped()` and `global()`
Multi-tenant data isolation is enforced at the database abstraction layer through `@poc/sdk`:
- **`scoped(db, workspaceId)`**: Wraps D1 database access with an immutable workspace identifier. Automatically binds and appends `WHERE workspace_id = ?` predicates to all `select`, `first`, `insert`, `update`, `delete`, and `count` operations on tenant tables. Raw SQL queries are validated to prevent cross-tenant subquery smuggling or un-predicated access.
- **`global(db, table, reason)`**: Explicit opt-in for declaring and accessing platform-wide tables (e.g. system configurations, global catalogs), requiring an architectural justification recorded in code and verified by schema conformance.
- **Atomic job and lease concurrency**: Concurrent operations (such as queue claiming in `queue-jobs`) use single atomic `UPDATE ... WHERE ... RETURNING *` queries to prevent double-claim races.

### 2. Continuous AST Query Linter (`lint:tenant`)
The repository enforces tenant boundary isolation continuously via `pnpm lint:tenant` (`scripts/lint-tenant-queries.ts`):
- Automatically scans TypeScript source files across all 42 bricks against catalog-derived tenant migrations.
- Reads the SQL itself (AD-V2, story 0.7): every query string that touches a tenant table must carry a `workspace_id` predicate in its WHERE clause (an INSERT, a `workspace_id` column), whether it is run by `db.prepare(...)`, `scoped().raw()`, `global()` or `systemScope()`.
- Unscoped queries fail CI unless exempted by name with a reason: a `{ file, table, reason }` entry in `scripts/tenant-lint-allowlist.json`, or a `// tenant-lint: allow <reason>` comment above the query.

### 3. Untrusted Code & Isolate Boundaries
- **Manifest Trust Declarations**: Every brick manifest declares `trust: "first-party" | "untrusted"` (defaulting to `trust: untrusted` fail-closed; all repository bricks declare `trust: first-party`).
- **Isolation Enforcement**: Manifests marked `trust: "untrusted"` strictly require `isolation: "dispatch"` (`isolation: dispatch`, enforced by `ManifestSchema` in `@poc/assembler`).
- **Dedicated Workers via Dispatch Namespaces**: The assembler emits separate Worker folders (`bricks/<id>/`) with isolated `wrangler.jsonc` configs containing only declared bindings and secrets. Untrusted bricks are mounted in the host Worker via service binding proxy routes (`BRICK_<ID>`), preventing ambient access to host secrets or other tenants' environments. First-party bricks run in the host isolate for latency and cost optimization.
- **Scripting Sandbox**: User-provided script execution in `scripting-sandbox` is delegated to an isolated Worker loader or dispatch namespace with strict CPU and wall-clock limits (UC6.6), fully replacing legacy `new Function` / regex blocklist execution.

### 4. Tenant Boundary & Route Exemption Policy (UC6.4)
Every mounted route in an assembled project is subject to the cross-tenant fuzz harness (`packages/assembler/test/cross-tenant.fuzz.test.ts`). Apart from the known failures registered below, the harness checks that:
1. Workspace A cannot read, modify, or enumerate Workspace B's records or secrets on any route of the app or any path emitted by `generateOpenApiSpec`.
2. All tenant-scoped routes enforce strict denial status codes (`401`, `403`, `404`, or `400`) when targeted by another workspace.
3. Every operation preserves byte-identical tenant table snapshots for unassociated workspaces.

#### Exemptions and known failures
There is no blanket route exemption list any more (the old `ROUTE_EXEMPTIONS` set is gone), and the suite does not claim that every route passes: today's violations are listed in the registry below. A route is left out of an attack only in one of these ways, each with a reason that the report lists:
1. **`PUBLIC_ROUTES`** in the test: routes that answer without a signed-in user by design (health and OpenAPI, `/api/auth/*`, webhook ingress, public SSO login, public profile lookup). They are skipped only by `UNAUTH`; every other attack still runs on them.
2. **The not-attacked list** in `evidence/cross-tenant-fuzz.json` (`notAttacked`): `ALL` entries of the route table (middleware, and catch-all handlers such as core-auth's `/api/auth/*`), and `ID_GUESS` on routes where no B row id fits a path param after seeding. Admin-class patterns that match no mounted route are listed in `adminClassNotMounted`.
3. **The known-failures registry** (`packages/assembler/test/attack-suite.known-failures.json`): violations that exist today, each tied to the story that fixes it (see below).

To change any of these, edit the list in the test or the registry and give the reason; a reviewer sees it in the diff and in the evidence report.

#### Cross-tenant attack suite and known-failures registry (story 0.5)
The same test file now runs a wider attack suite. It reads the real route table of the assembled `max-compatible` Hono app (every method and sub-route; every OpenAPI path is attacked at its exact path too), seeds data for Alice (workspace A), Bob (workspace B) and Carol (a plain `member` of A) in every brick that accepts a generated POST, and harvests B's real row ids from B's tenant tables. Each route then gets these attack classes, judged by one oracle (no B secret in the body unless the attacker sent it, B's tenant rows unchanged, plus the status rules below):

- `HEADER_B`: Alice names B (or malformed A+B values) in `x-workspace-id`; on a guarded route it must be 400/401/403/404.
- `QUERY_B`: Alice, header A, `?workspaceId=B`.
- `BODY_B`: Alice, header A, `workspaceId`/`workspace_id`/`workspace` = B and `id` = a B record id in the JSON body of every POST/PUT/PATCH.
- `ID_GUESS`: Alice, header A, path params filled with B's real ids; must be 400/401/403/404.
- `ROLE_ESCALATION`: Carol calls every admin-class route (the `ADMIN_CLASS` list in the test); must be 401/403 and leave A unchanged.
- `UNAUTH`: no `x-test-user` on every route not in `PUBLIC_ROUTES` (each with a reason); must be 401/403. A 400 "Missing workspace context" is accepted only on a guarded route (behind `workspaceMiddleware`), and a 404 only on an OpenAPI path that has no handler.

Violations that exist today live in `packages/assembler/test/attack-suite.known-failures.json`. Since story 0.11 the registry is empty (`"entries": []`): the 0.11 entries went with the quarantined bricks, which are no longer in `max-compatible`, and the seven `PROPOSED-14` `ID_GUESS` entries were fixed (schedule history, document chunks and extractions, script executions and webhook endpoint deliveries now check the parent row in the caller's workspace and answer 404; notification read/delete answer 404 for another user's notification instead of a fake 200). Each entry names the exact `method`, `route` (no wildcards), `attack`, the fixing `story` and a one-line `reason`. The suite fails on any violation that is not in the registry (`NEW_FAILURE`) and on any entry whose attack no longer fails (`STALE_ENTRY`). So a fixing story (0.6, 0.7, 0.9, 0.10, 0.11, 0.14, 1.4 or a `PROPOSED-n` ticket) must delete its entries in the same change that fixes them, and nobody can add a new leak without adding a reviewed entry. Routes or attacks that were not run (public routes, params with no B id after seeding, admin-class routes not mounted in `max-compatible`) are listed with their reason in `evidence/cross-tenant-fuzz.json`.
